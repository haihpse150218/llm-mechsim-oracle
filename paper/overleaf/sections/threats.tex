\section{Threats to validity}\label{sec:threats}

\paragraph{Construct validity} Correctness is defined by our oracle and by hand inspection by the author. The DESIGN rules encode engineering knowledge that we wrote. We verified the reference designs numerically (Jansen's foot path, the lambda straight segment, the Peaucellier line), but the rule set has not been reviewed by an independent mechanical engineer. Each rule is a textbook condition (Grashof, assembly of planetary sets, tangential Geneva entry, transmission and pressure angles) or a published dimension set with its source cited, and all rules are in the public repository for inspection. The marker contract is a precondition of the oracle and may change how models write simulators. Generators were told the contract in advance; simulators found in the wild expose no markers or \texttt{SIM.params} and cannot be checked without it. The contract is a small addition to a common practice, since the generation tool we started from already requires a pure \texttt{render(t)}: only the markers and the declared parameters are new. The VLM baseline is the larger generator model looking at a contact sheet of 12 still frames. A stronger model, or video input, might find more of the visible faults. It could not find faults that leave no visual trace, such as the planetary tooth-count violation, and these are the main argument for an executable gate. Errors outside the contract, such as the Geneva disc, are invisible to the oracle, so ``passes the oracle'' does not mean ``correct'' in every respect. The feedback levels are produced by transforming the oracle's text. Location-only and coarse feedback still contain the measured magnitude of each failed check, which a repairer can partly exploit (Section~\ref{sec:discussion}).

\paragraph{Internal validity} Repairers were not allowed to run code, so that all arms received information only through feedback. Self-refinement by an agent that can execute its own page might do better. Agents ran as sub-agents of Claude Code with that tool's system prompt, not as raw model calls. One of 155 phase-5 repair attempts ran a command despite the instruction; we kept it in the data. The design evolved over phases (Section~\ref{sec:design}), and the feedback levels were introduced after seeing phase-4 results. To limit the resulting risk of tailoring, phases 6 and 7 re-used the exact file-runs and stopping rules of phase~5 and added mechanisms chosen \emph{before} their generations were seen.

\paragraph{External validity} The repair experiments used only two models of one vendor. A generation-only check with two DeepSeek models (phase~8) reproduced the RQ1 error pattern on Jansen and lambda, but it was small (19 runnable simulators) and called the models through their API rather than as Claude Code sub-agents. Repair with another vendor's model, and hence RQ3 and RQ4, is the most important missing replication. Because the oracle, prompts and feedback transformations are model-independent and published, it requires only new repair runs; the API runner used in phase~8 is included in the repository. The mechanisms are planar, single-input and textbook-sized. The significant RQ4 effect rests on two mechanisms with published dimensions (Jansen and lambda). The relation-type mechanism (Peaucellier--Lipkin) produced no natural errors, so it could not be tested on real faults. Simulators followed a reduced contract derived from one generation tool.

\paragraph{Conclusion validity} Samples are small (22 + 6 file-runs for repair). Repetition~2 contains the files of repetition~1, so file-runs are not independent. We report exact tests, Holm-corrected pairwise comparisons and an analysis that counts each source file once; the main effects (full oracle feedback versus all other arms; the model $\times$ feedback interaction) remain significant under it. Several pairwise differences, such as location-only versus coarse and oracle versus VLM with panel on mutants, are not significant, and we do not claim them.
